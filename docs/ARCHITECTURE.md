# Architecture Overview

This repo has now converged from a template into a local `computer-use` project. The mainline remains the Swift-implemented macOS automation MCP server, with new experimental Windows and Linux runtimes added, each exposing the same set of 9 Computer Use tools via standalone Go binaries.

## Current Directory Structure

- `apps/OpenComputerUse`
  Main entry point, responsible for the `mcp`, `doctor`, `list-apps`, `snapshot`, `call`, `turn-ended` and other CLI commands, as well as global flags such as `-h` / `--help` / `-v` / `--version`; when launched without arguments it first checks permissions, and only enters the app-mode permission onboarding window (which has no Dock icon) when something is missing; `doctor` likewise only launches this onboarding UI when it detects a missing permission.
- `apps/OpenComputerUseFixture`
  Local GUI fixture app, used to host low-risk, predictable click / input / scroll / drag verification paths.
- `apps/OpenComputerUseSmokeSuite`
  End-to-end smoke runner that launches the fixture and the MCP server and really calls the 9 tools over JSON-RPC; it also supports a standalone visual cursor idle smoke that asserts, via a cross-process observation file, that while waiting for the next move the tip is anchored with a tiny rotate wobble, rather than drifting laterally.
- `apps/OpenComputerUseWindows`
  Experimental Windows runtime. It does not depend on Swift or a `.app` bundle; it is a single Go exe with an in-process UI Automation + Win32 implementation (no PowerShell/.NET, no CGO). The build artifact is `open-computer-use.exe`, distributed as a bundled artifact under `dist/windows/<arch>/` of the existing npm package.
- `apps/OpenComputerUseLinux`
  Experimental Linux runtime. It does not depend on Swift or a `.app` bundle; the Go CLI/MCP entry process connects directly to AT-SPI2/D-Bus in-process (single binary, zero runtime dependencies). The build artifact is `open-computer-use`, distributed as a bundled artifact under `dist/linux/<arch>/` of the existing npm package.
- `packages/OpenComputerUseKit`
  Core library, including:
  - MCP stdio transport and tool registry
  - app discovery
  - Accessibility / window snapshot
  - keyboard and mouse input simulation
  - software cursor overlay
  - fixture test bridge
- `scripts/`
  Repo-level automation commands, including the smoke test, the `.app` packaging entry point, the Windows `.exe` / Linux binary build entry points, and the npm distribution scripts.
- `skills/`
  An installable skill for agent runtimes. Currently `skills/open-computer-use/SKILL.md` serves only as a lightweight entry point and table of contents; installation, MCP/CLI usage, troubleshooting and other details are split into adjacent `references/` files that are loaded on demand; `scripts/package-skill.sh` is responsible for validating and packaging the `.zip` / `.skill` artifacts.
- `plugins/`
  The plugin form for agent hosts. `plugins/open-computer-use/` carries both the Codex (`.codex-plugin/`) and ZCode (`.zcode-plugin/`) manifests, the `.mcp.json` and launch scripts shared by both, and a self-contained copy of the skill (ZCode validates that component paths do not escape the plugin root); the ZCode marketplace manifest lives in `marketplace.json` at the repo root.
- `docs/`
  Architecture, collaboration conventions, and project constraint documents.

## Runtime Layers

### 1. App Mode Layer

- In default app mode, `OpenComputerUse` launches `PermissionOnboardingApp`.
- The app bundle runs as an `LSUIElement` agent-style app: by default it exposes no persistent Dock icon, but can still display the permission window on demand.
- When a user runs the macOS `open-computer-use mcp`, `doctor`, `call`, `snapshot`, or `list-apps` from a terminal, the CLI first launches the hidden app agent of the same `.app` bundle via LaunchServices and forwards the request over a Unix domain socket under the user's temporary directory; the process that actually invokes Accessibility, ScreenCaptureKit, and the action tools is always `Open Computer Use.app`, never the iTerm / Terminal / Node launcher.
- Since 2026-08-25 macOS provides **display-level commands** (`screenshot` / `cursor-position` / `input` / `record`; command names, arguments, and output structure are aligned with the Linux/Windows counterparts, implemented in the Kit's `DesktopCommands.swift`, with parsing as pure functions covered by the unit test `DesktopCommandTests.swift`). These four commands likewise execute through the app agent proxy, so the TCC grants for Screen Recording / Accessibility land on the `.app` bundle identity; the bare CLI build executes in-process and reports a clear error when a permission is missing (pointing to `open-computer-use doctor` or System Settings). Platform details:
  - `screenshot [--output x.png]`: per-display `CGDisplayCreateImage` composited onto a full-desktop canvas by Quartz global bounds (multi-screen composition, 1x output); the PNG is written to a file or printed as base64; a `CGPreflightScreenCaptureAccess()` preflight runs before execution.
  - `cursor-position`: `CGEvent(source: nil).location` reports the pointer position in the top-left-origin desktop coordinate system + the combined desktop size, emitting JSON isomorphic to the Linux/Windows output.
  - `input <move|click|drag|scroll|type|key|wait>`: CGEvent delivery to `.cghidEventTap` (reusing `KeyPressParser`/`keyboardUnicodeChunks`); a new, independent gate `OPEN_COMPUTER_USE_MACOS_ALLOW_FOREGROUND_INPUT=1` (default off, semantics aligned with Linux `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS` / Windows `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOREGROUND_INPUT`) is required, and when enabled it also demands the Accessibility permission; `wait` is not gated.
  - `record <start|stop|discard|polish|status>`: prefers `ffmpeg avfoundation` on PATH (demo-quality H.264 mp4 aligned with Linux/Windows / Cursor RecordScreen: veryfast + crf 17 + High + faststart, supporting `--fps` / `--quality demo|draft|proxy` / `--draw-mouse`), falling back to `/usr/sbin/screencapture -v` (`.mov`; these quality switches are ignored) when it is missing. While recording, display `input` appends to `<output>.events.json`; `record polish` (or `start`/`stop --polish`) applies ffmpeg+ASS post-processing (accepts `--engine` for alignment with the Linux/Windows CLI; the full CPU compositor lives on the Go side), with `draw-mouse=0` (`-capture_cursor 0`) as the default when `--polish` is set. `discard` stops and deletes the artifact and sidecar; `stop --save-as` renames (and migrates the events sidecar where possible); `--pidfile` also takes effect at start.
- The CLI and MCP proxy forward `OPEN_COMPUTER_USE_*`-prefixed environment variables from the calling process along with the request to the app agent, temporarily overriding the agent's environment only while that request executes; this lets the process-level safety gate and debug switches for `click_method=global` still take effect per caller configuration under the app-agent architecture.
- The main window is responsible for rendering the two permission cards for `Accessibility` / `Screen & System Audio Recording`, the `Allow` / `Done` states, and state convergence after relaunch; it closes automatically once both permissions are complete and no longer asks the user to quit manually.
- The auxiliary drag panel jumps to the corresponding `System Settings` page; after clicking `Allow`, the panel performs a spring + curved-frame entrance from the button position in the main window, then settles onto the bottom edge of the `System Settings` content area. By default the panel stays centered below the content area on the right side of the window and fixed near the window's bottom edge, no longer relying on live-scanning the `+ / -` control rows inside the permission page; in window stacking order it is explicitly placed above the current `System Settings` window to avoid being covered by the permission list content, while minimizing interference with System Settings' own scroll region. An explicit back button was also added inside the panel, letting the user interrupt the current guidance, return to the onboarding main window, and reselect a permission step.
- Permission state merges TCC persistent grant records with the current app process's runtime preflight: if any matching client is already granted in TCC, it is treated as granted, avoiding inconsistent views of the grant state between CLI subprocesses and the GUI app; if the current `.app` process has already passed `AXIsProcessTrusted()` / `CGPreflightScreenCaptureAccess()`, it is also immediately treated as granted, preventing stale or mismatched TCC path records from keeping the onboarding overlay up. Official releases still treat the `Open Computer Use.app` built by CI as the source of truth, while local debug/dev packaging is now explicitly named `Open Computer Use (Dev).app`, and the dev bundle prefers the current dev copy at runtime to avoid two identically named entries appearing in System Settings.

### 2. MCP Layer

- The external transport for MCP hosts remains `stdio`; between the macOS terminal CLI and the `.app` app agent there is an additional local Unix domain socket proxy layer, ensuring that the real automation runs under the app bundle's permission identity.
- Unless `OPEN_COMPUTER_USE_VISUAL_CURSOR` is explicitly disabled, the `mcp` command switches to a minimal AppKit runtime: the main thread keeps an event loop to host the overlay UI, and the stdio server still reads and responds serially on a background thread.
- Request framing uses one JSON-RPC message per line.
- Currently supported methods:
  - `initialize`
  - `notifications/initialized`
  - `notifications/turn-ended`
  - `ping`
  - `tools/list`
  - `tools/call`
- `notifications/turn-ended` is an explicit turn-boundary hook in the open-source edition; on receipt it clears the visual cursor overlay in the current process. The CLI `open-computer-use turn-ended [payload]` also notifies the running AppKit MCP process, via a macOS distributed notification, to perform the same kind of cleanup, used to receive the after-agent payload of Codex's legacy notify.

### 3. Tool Service Layer

- `ComputerUseService` maps Computer Use tool requests onto local capabilities, and `ComputerUseToolDispatcher` converges argument parsing and service-method dispatch for the 9 tools into a single layer shared by the MCP server and `open-computer-use call`.
- `list_apps` pulls app bundles from the standard application directories via a Spotlight metadata query and reads system metadata such as `kMDItemUseCount` / `kMDItemLastUsedDate_Ranking`; it then merges with `NSWorkspace`'s running apps to output a "currently running + used within the last 14 days" view.
- `get_app_state` prefers the real AX / window screenshot; a real app must have both a non-minimized `AXWindow` and a matchable on-screen `CGWindow`. If the target app is merely hidden or temporarily has no on-screen window, it first does a best-effort unhide / activate / `open -b` / `AXRaise` and brief retry, mirroring the official `computer-use` behavior of pulling Lark / Electron windows back before capturing; if it still cannot match after recovery it returns the official-style `Apple event error -10005: cgWindowNotFound`, no longer disguising the application root node or a screenshot-less window as an operable state. When the target is the in-repo fixture app, it falls back to the synthetic state exported by the fixture. The real AX tree renders at most 1200 nodes and 64 levels of depth by default on macOS, Linux, and Windows; explicit `get_app_state` / `snapshot` calls can override the budget via `max_tree_nodes` / `max_tree_depth`, while action-tool refresh results still use the default budget. Snapshot text is truncated to 500 characters by default; explicit `get_app_state` / `snapshot` calls can override with a positive integer or `"max"` via `text_limit`, while action-tool refresh results still use the 500-character default. For deep UI such as Electron/WebView, empty `AXGroup` / `AXUnknown` wrappers are collapsed and `AXScrollToVisible` noise and empty-string attributes are filtered, so that action-critical input fields are not pushed out of the node budget by semantically empty containers; however, `AXPress` / `AXConfirm` / `AXOpen` child nodes inside generic nodes form a text-summary boundary, preventing multiple clickable options from being merged into a single container. Such action nodes, if their frame is valid and their size compact, are kept as `button` elements with a window-relative `Frame`, using short-text descendants as the button summary, so that both icon-only and text web controls get distinguishable `element_index` values, while zero-sized generic click containers or ones covering a large area of the page are still filtered out. For controls like the native open panel / Finder column view that keep their content in `AXContents` / `AXVisibleChildren`, visible file items are also included in the element tree.
- The MCP `tools/list` descriptions / input schema have currently converged on the copy and parameter surface of the official `computer-use`'s 9 tools, minimizing drift between host-side prompts and the tool surface.
- `open-computer-use call <tool> --args '{...}'` directly prints an MCP-style JSON result; `open-computer-use call --calls '[...]'` / `--calls-file <path>` executes the tool calls in the JSON array sequentially within the same process, reusing the same `ComputerUseService` in-memory state, so action tools after `get_app_state` can keep using the `element_index` from the same round of snapshot. Sequential execution defaults to sleeping 1 second between successful adjacent operations, overridable with `--sleep <seconds>`; it stops when it encounters a tool result with `isError=true`.
- For the `get_app_state` / action tool entry points against real apps, only one layer of password-manager bundle denylist is currently kept: a directly passed bundle-id returns a safety denial immediately; name matching does not resolve to these apps by default. Terminals, Chrome / Atlas, and system components are no longer built-in blocked targets.
- Element frames for ordinary apps are currently output in window-relative coordinates with "the window's top-left corner as the origin", making it easier to later unify `element_index` and screenshot coordinates into a single reference frame.
- Before and after performing a real action, `click` / `set_value` additionally drive a transparent `SoftwareCursorOverlay` window: the move phases of both now share a single heading-driven, official-style motion core, explicitly feeding "the current cursor heading" and "the final resting pose" to the router, preferring to generate C-shaped / one-sided large-arc trajectories that turn around first when needed and then advance along the heading; on first display the start point is generated from the AppKit global `(0,0)` window origin in the official binary's fresh state, and subsequent actions keep reusing the previous frame's visible tip. The cursor actually displayed is no longer the path sample directly, but passes through an independent visual dynamics state that continuously advances the visible tip, velocity, angle, and fog/offset. `click` ends with a click pulse followed by a more pronounced but still very small rotate wobble; `set_value` only does settle / idle, with no pulse; after both finish, they continue to hold the idle state at the target point, and while waiting for the next action the tip stays anchored with only a perceptible small-angle wobble; cleanup happens only after 30 continuous seconds without a new action, so consecutive tool calls do not repeatedly restart from a fresh `(0,0)`; if the host emits `turn-ended` at the end of a task / turn, the cursor disappears immediately and this round's positional state is cleared.
- The overlay's visual style no longer crops `SoftwareCursor` sprites from the official app bundle itself; the main MCP runtime now preferentially renders the `assets/cursor/official-software-cursor-window-252.png` baseline kept in the repo, falling back to the procedural pointer/fog fallback inside `OpenComputerUseKit` only when the asset is missing. The hit-point anchor remains fixed on the same set of tip-offsets in the `126x126` canvas; the glyph's own neutral heading continues to use the official baseline's `-3π/4`. The main runtime overlay window moves in AppKit global coordinates, so before feeding AX / `CGWindowList`-produced y-down screen-space click targets to the overlay, they are first converted to the AppKit global coordinates of the corresponding screen; path routing uses the actually visible AppKit forward heading on screen, and before entering the visual dynamics / render state the velocity's y axis is flipped back to CursorMotion's y-down screen state, after which the AppKit drawing layer performs the angle and `dy` flip. The procedural fallback retains the neutral artwork correction, aligning its natural outline axis with the official baseline's `-3π/4` forward direction.
- The overlay's level is no longer fixed at `.floating`; it now follows the target window id / layer hit by the snapshot, placing itself above that target window rather than crudely forcing itself to the very top of all foreground apps.
- The overlay's curved path is no longer generated from a fixed Bezier template alone; the current mainline adopts a heading-driven candidate family under reverse-engineering constraints, keeping only the `direct` / `turn` / `brake` / `orbit` families that reliably produce a one-sided main arc, and retaining the target-window hit strategy as a tie-break among same-class candidates. Candidate generation no longer depends on historical reverse-engineering artifacts and is driven directly by the behavioral constraints.
- The overlay's progress curve is no longer a fixed `easeInOut` either; the mainline now reuses the official spring/`VelocityVerlet` shape with `response=1.4`, `dampingFraction=0.9`, `dt=1/240`, and the default move duration aligns with the recovered close-enough endpoint-lock time `343 / 240 = 1.4291667s`, no longer applying extra compression by path distance.
- The overlay no longer relies on a stopgap `terminal settle` patch to fix the tail; the mainline now uniformly switches to a two-layer model where "the path layer supplies the target point and the visual dynamics layer supplies the visible pose", so the end of a move, the pulse, and idle all share the same state, and the endpoint no longer ends with an in-place angle flip after it is locked.
- The overlay's render inputs have also been extended from a single `rotation` to `rotation + cursorBodyOffset + fogOffset + fogScale`, so that velocity lag is actually visible on screen instead of existing only in the main loop's internal state; `rotation` now approximates the binary's layered `SoftwareCursorStyle.angle + CursorView._animatedAngleOffsetDegrees` decomposition, no longer squashing "the main heading that follows the direction of motion" and "the small wiggle offset" into a single constrained small angle.
- Action tools follow a "non-invasive first, physical pointer paths explicitly opt-in" strategy for ordinary apps:
  - `perform_secondary_action` only executes AX actions that the target element already exposes; an invalid action returns the official-style `... is not a valid secondary action for ...`, and the fixture's `Raise` path no longer prepares global physical pointer input for testing
  - `set_value` first uses `AXUIElementIsAttributeSettable(kAXValueAttribute)` to determine whether the target is really a settable-value element and only calls `AXUIElementSetAttributeValue` when it is settable; when it is not settable it returns an official-style non-settable error, without falling back to keyboard input, the clipboard, or an unpublished text-replacement API
  - `click.click_method` is an optional extension of the open-source edition, supporting `auto` (default), `accessibility`, `app_post`, `sky_click`, and `global`. When no argument is passed, the original automatic routing is still used; explicit modes do not silently fall back to other implementations. `accessibility` only accepts `element_index`; the other mouse paths can use the computed landing point of an `element_index` or raw `x/y` coordinates.
  - The `auto` left-button path for element-targeted `click` first tries `AXSelectedChildren` selection on a native list, then tries genuinely semantic activation actions such as `AXPress` / `AXConfirm` / `AXOpen`; if the target itself is not clickable, it keeps trying its descendant AX elements (e.g. a cell exposing `AXOpen` under a Finder sidebar row) and AX hit-test results near the hit point, and finally enters the existing non-AX branch: using `postToPid`-targeted mouse events when the global pointer environment variable is not enabled, and using global HID events directly when it is. Activation-only fallbacks such as `AXRaise` / `kAXMainAttribute` / `kAXFocusedAttribute` are only allowed on window-level elements, preventing ordinary static text or containers from misreporting "got focus" as "click handled"; `click_count > 1` also prefers repeating an available AX action.
  - Explicit `click_method=accessibility` only executes the AX semantic actions above; explicit `click_method=app_post` bypasses AX candidates and descendant scanning and sends `mouseMoved` / down / up directly to the target process via `CGEvent.postToPid`; explicit `click_method=sky_click` only accepts left-button single/double clicks on macOS — it verifies that the current snapshot's `CGWindowID` is still owned by the same PID and on-screen, and only uses `SLPSPostEventRecordTo` to briefly put the target app into a synthetic-active state, never sending a defocus record to the real foreground app, then sends the target move, a `(-1,-1)` primer, and the real down/up following a Chromium-compatible recipe. Every mouse event is delivered both through the dynamically resolved `SLEventPostToPid` and the public `postToPid`, carrying window-local location, PID/window, and click-group fields; after the renderer settles, only the target's synthetic-active state is revoked. The action-result snapshot refresh of `sky_click` also forbids activate / `AXRaise` recovery and fails directly if the target state is transiently unreadable. It does not alter `auto`, and no step falls back on failure. Explicit `click_method=global` likewise bypasses AX but sends system-level pointer events through `.cghidEventTap`. `global` additionally requires `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1` to be set, otherwise the request is rejected before moving the visual cursor or sending input.
  - For renderer-synthesized summary `text` rows, `click` no longer clicks the parent container's center by default; such elements use a left-side safe anchor. Descendant candidates of ordinary rows/containers/text also filter out compact hover actions on the right side (e.g. the "done" checkmark in a Lark / Electron conversation list), avoiding mis-operating a main-row click into a side action; the WebArea synthesized text of Electron/Lark-type apps preferentially looks for the adjacent row-level `AXPress` ancestor and executes it silently, avoiding clicking the row with a physical mouse. Browser WebAreas (e.g. Chrome/GitHub) do not take this Electron-scoped row-level ancestor click optimization and keep the generic link/container click path. If the hit point resolves only to a page-covering Electron/WebArea-level AX element, it no longer keeps scanning descendant candidates of the whole large container, avoiding a row click being hijacked by a far-away clickable element.
  - `AXUIElementCopyElementAtPosition` performs coordinate hit-testing, trying to reverse-resolve a coordinate click into an operable AX element
  - `CGEvent.postToPid` delivers keyboard events targeted at the process, avoiding stealing the foreground for `type_text` / `press_key`; `type_text` groups text by Unicode extended grapheme cluster into small batches of `keyboardSetUnicodeString` events, preventing Chinese punctuation, emoji / surrogate pairs, and combining characters from being split into individual UTF-16 code units and arriving out of order or deformed in Electron rich-text input fields. If the current focused element's `AXValue` is settable, `type_text` preferentially appends as editable content and writes it back to `AXValue`, covering the case where Feishu / Electron rich-text input fields receive background keyboard events unreliably, and it filters known placeholder hints so that a placeholder is not concatenated into the draft; when the settable query itself fails (e.g. -25205) it is treated as "settable unconfirmed" and the keyboard fallback chain continues, instead of throwing the raw AX query error to the caller; if the current focused element is not an editable text target, `type_text` errors out, asking to click the text input area first or use `set_value`, no longer treating an ineffective background keyboard delivery as success; the xdotool parser for `press_key` covers the common `BackSpace`, `Page_Up`, `Prior` / `Next`, `F1...F12`, and `KP_*` aliases in the official binary's key table
  - `scroll.pages` aligns with the official `1.0.755` `number` schema and supports fractional pages; for integer pages when the target exposes `AXScroll*ByPage`, the AX action is preferred, otherwise a scroll event is sent targeted at the target process via `CGEvent.postToPid`
  - `drag` remains a coordinate-only API, but no longer uses global `.cghidEventTap` mouse events by default; it now defaults to `CGEvent.postToPid`-targeted mouse move / down / dragged / up events, avoiding moving the user's real hardware cursor; the `x/y` of these coordinate tools is first interpreted as screenshot pixel coordinates, then mapped back to window point / Quartz global coordinates by the ratio between the screenshot pixel size and the target window bounds, avoiding Retina windows where 2x pixels are mistaken for 1x points and the click lands at the wrong position
  - `click` / `scroll` / `drag` do not go through the global `.cghidEventTap` under the default configuration where the environment variable is not enabled, so they never move or steal the user's real mouse; `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1` is the process-level safety gate for global pointer capability, and explicit `click_method=global` must still pass through this authorization. The default path no longer calls `NSRunningApplication.activate` for fallback

### 4. Fixture Bridge

- `OpenComputerUseFixture` writes its own window and element state to a temporary JSON file.
- For the fixture's `get_app_state` and a few test-only actions, an explicit command channel is used through `FixtureBridge`.
- This bridge only serves the in-repo deterministic smoke path; it is not a capability boundary aimed at real third-party apps.
- Because the fixture launched as a bare SwiftPM executable has no stable bundle identifier, `list_apps` injects an internal synthetic identifier only for `OpenComputerUseFixture`, ensuring the smoke suite can still cover `list_apps`, while ordinary third-party apps are still output with their real bundle id.

### 5. Windows Runtime

- The Windows runtime lives in `apps/OpenComputerUseWindows` and maintains the CLI, `call --calls` sequence, MCP JSON-RPC, tool schema, and in-process snapshot cache in Go.
- The build entry is `scripts/build-open-computer-use-windows.sh --arch arm64|amd64`, outputting by default to `dist/windows/<arch>/open-computer-use.exe`; the npm release package embeds the two Windows artifacts into the existing root/alias packages, and the Node launcher auto-selects based on `process.platform/process.arch`.
- The Windows runtime is a single Go exe with zero external dependencies: all 14 tools are in-process Go implementations, no PowerShell/.NET, no CGO (dependencies limited to `golang.org/x/sys/windows` and `go-ole`); `runtime.ps1`, the C# helper, and `go:embed` have been removed. Layering: `native_win32.go` (window enumeration / SendInput / PostMessage / GDI / activation / .lnk / EM text chain), `native_capture.go` (pure-Go WGC/print/gdi screenshot chain), `native_uia.go` (UIA COM bindings + dedicated COM thread + tree rendering), `native_actions.go` (element fingerprint / FindElement / seven-action dispatch), `native_backend.go` (tool dispatch), `main.go` (CLI/MCP/service layer and gates). `OPEN_COMPUTER_USE_WINDOWS_BACKEND` is deprecated: when set, it only prints a one-line deprecation warning and is then ignored (pinned by unit tests).
- **Process model: sacrificial-subprocess isolation (op worker).** Soak testing proved that this machine's DWM/driver stack has an asynchronous out-of-bounds write: during the unstable window right after a window move, any native window-reading operation (including UIA tree traversal as well as WGC/PrintWindow screenshots) can corrupt the calling process's Go heap — Marshal starts reporting NUL, reflect panics — and once it happens the process is unusable; isolating only the screenshot chain is not enough to protect the main process. Therefore the long-lived MCP/CLI process only does JSON codec and service-layer gating; each tool operation is serialized to `psRequest` JSON and handed to a short-lived subprocess of the same exe (`opencomputerusewindows.exe op`) to execute, with a one-line `psResponse` JSON returned on stdout; if the subprocess crashes / its output contains NUL / it times out (60s), it retries (up to 3 times, 600ms apart, waiting for the window move to settle), and if it still fails it falls back to in-process execution (consistent with the old behavior, zero new error copy). The screenshot chain is further isolated into a grandchild process (hidden `capture` subcommand, 20s timeout); when the `go test` binary and the exe are unavailable, it automatically falls back to in-process. Domain errors always pass through `psResponse.Error` byte-for-byte, and the protocol surface (`psRequest`/`psResponse` field names and order) is unchanged.
- Measured latency (single MCP call, median of 3 rounds): `get_window` ~10ms, `list_windows` ~400ms, `get_window_state` (tree only) ~390ms, `get_window_state` (tree + screenshot, with wgc healthy) ~540ms (print fallback ~1.8s), `type_text` (action + snapshot refresh) ~2.0s, `list_apps` ~3.5s (dominated by COM resolution of 149 .lnk files in the Start Menu). Compared with the old PS: one-shot ~570ms, daemon hot path ~130ms / full tree ~790ms; the fixed overhead of the op subprocess is a cold UIA COM initialization each time (~300-400ms), bought in exchange for main-process heap safety. The WGC chain was re-tested healthy on 2026-08-23: forced wgc first frame ~180ms, wgc soak 3×10 PASS. The "no frame arrived" observed late at night was, after cross-validation (an older git version's PS OCUCapture can capture on the same machine, a new window of the same exe works, a 60-move stress test does not reproduce it, and the machine was not restarted), classified as a single-window-instance event rather than a system-level refusal; the same day an out-of-bounds cursor vtable call on the frame pool was demonstrated and removed (IGraphicsCaptureSession2 is not exposed on build 26200, and the retired PS implementation never called it either).
- The Windows runtime by default only connects to already running apps; it does not automatically `Start-Process` when `get_app_state` cannot find the process, and it does not allow the `SetFocus` secondary action by default; these two foreground-stealing paths require `OPEN_COMPUTER_USE_WINDOWS_ALLOW_APP_LAUNCH=1` and `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOCUS_ACTIONS=1` respectively, explicitly enabled. `type_text` by default prefers sending `EM_SETSEL` / `EM_REPLACESEL` to the child HWND of a writable text control, and no longer goes through the UIA `ValuePattern.SetValue` fallback by default since it may trigger foreground activation; the old behavior requires setting `OPEN_COMPUTER_USE_WINDOWS_ALLOW_UIA_TEXT_FALLBACK=1`. The UIA pattern and Win32 message fallbacks are themselves still best-effort: many controls can respond in the background, but Windows has no background keyboard/mouse input model equivalent to macOS AX for all GUI toolkits.
- The protocol surface of these 9 tools is consistent with the macOS mainline: `list_apps`, `get_app_state`, `click`, `perform_secondary_action`, `scroll`, `drag`, `type_text`, `press_key`, `set_value`. Among them, element-targeted actions preferentially reuse the runtime id / automation metadata from the previous `get_app_state` round, while coordinate actions use screenshot/window-relative coordinates.
- Since 2026-08, the protocol surface aligns with the official Codex `window2` API (per the official `computer-use` plugin's `docs/api.md`), adding 5 official same-named tools on top of the 9 legacy tools: `list_windows`, `get_window`, `launch_app`, `get_window_state`, `activate_window` (14 in total). The `id` in `Window = {app, id, title}` is an opaque HWND integer on Windows (CGWindowID on macOS, where `launch_app` is already implemented; an X window id on Linux); action calls locate the window via the optional `window` parameter (or `window_id`), falling back to the legacy `app` key-window semantics when omitted.
- Key points of window2 semantics: `get_window_state` returns a structured `WindowState` (`accessibility.tree` + `focused_element`/`selected_text` gated by `include_text`, `screenshots[]` with data URLs carrying `id/originX/originY/zIndex`); coordinate actions may pass `screenshotId` to bind the observation moment, stale ids are rejected before execution ("stale screenshot id; re-observe..."), and any successful action invalidates the window's cached screenshot ids. v1 has only one full-window screenshot per state; multiple bounded screenshots (transient UI / modal) are not yet implemented. Since 2026-08-22, coordinate input (click x/y, coordinate scroll, drag) aligns with the official observation gate (service layer, `bounds_gate.go`): a window-targeted coordinate action must be preceded by an observation (`call get_window_state before issuing coordinate input`), the observation must include a screenshot (`... with include_screenshot before ...`), any change in the window bounds since the observation is rejected (`window bounds changed; call get_window_state before continuing`), and coordinates must fall within the screenshot pixel bounds (`(x, y) is outside screenshot bounds`); element_index targeting and legacy `app`-keyed flows are unaffected by the gate. Aligned in the same batch: explicit rejection of `mouse_button=right` + `click_count>=2` ("right double click is not supported"), a `type_text` limit of 8192 UTF-16 code units ("text is too large for SendInput ..."), and three AV-suite display names added to the deny list (avg internet security / avast premium security / bitdefender security center, case-insensitive substring match). The window activation sequence aligns with the official one: `AttachThreadInput(attach)` → `AllowSetForegroundWindow(pid)` → `SetForegroundWindow` → detach (Go `setForegroundWindow`, semantically inheriting the retired PS implementation's `SetForegroundWindowReliable`), fixing the reliability issue where activation silently failed under the foreground lock and SendInput went into the wrong window.
- `scroll` supports the official coordinate-delta mode: `x/y` (window-relative) + `scrollX/scrollY` pixel deltas (negative = left/up), delivered via `WM_MOUSEWHEEL`/`WM_MOUSEHWHEEL` converted at approximately 40px/notch; the legacy `element_index + direction + pages` UIA Scroll mode is unchanged.
- `list_windows` enumerates Window control type child elements under the UIA root, covering secondary windows and modal dialogs of the same process; the `list_apps` response appends a structured apps array (running processes carry `windows[]`, plus installed apps enumerated from Start Menu `.lnk` files) beyond the legacy text lines.
- The official safety red lines have been implemented: `press_key` hard-rejects Windows/Meta keys (`super/win/cmd/meta/command/os/windows`, including chords); app resolution and `launch_app` (gated by `OPEN_COMPUTER_USE_WINDOWS_ALLOW_APP_LAUNCH=1`) enforce a deny list (terminal hosts, password managers, Windows security-class apps), with no exemption by any environment variable. `activate_window` is gated by `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOCUS_ACTIONS=1`.
- The macOS / Linux interface definitions (`ToolDefinitions.swift` / Linux `toolDefinitions()`) have been synced to the same 14-tool surface. macOS `launch_app` has a native path implemented (`AppDiscovery.launch`, NSWorkspace/LaunchServices): lookup by app name or Bundle ID, reuse of a running instance, background launch without stealing focus via `NSWorkspace.OpenConfiguration.activates = false`, returning `pid`/`bundleIdentifier`/`name`/`windows[]` (`CGWindowID` + optional title, title depending on Screen Recording authorization), reusing the existing app deny list (password managers), with no extra feature gate. The remaining 4 macOS window2 tools (`list_windows`, `get_window`, `get_window_state`, `activate_window`) and the `window`/`screenshotId`/coordinate-scroll parameters of the seven action tools have native paths implemented (`WindowManagement.swift` + `ComputerUseService`): the window catalog is based on `CGWindowListCopyWindowInfo` (on-screen, layer 0, non-zero size, `{app, id, title}`, `id` is the CGWindowID, title depends on Screen Recording authorization — title is omitted without authorization but id is always returned); window resolution order is stale-window (`staleWindowHandle(id): the window is no longer open; re-observe with list_windows.`) → host process already exited (nil check on `NSRunningApplication(processIdentifier:)`, `staleWindowHandle(id): the owning process is no longer running; re-observe with list_windows.`) → reusing the existing app deny list (password managers) → AX-identity liveness check (`WindowIdentity`, see `docs/design-docs/macos-window-identity.md` for the design: closed windows and AppKit helper windows linger long-term in the full CGWindow list; when the host app's AX window list has been read out completely, and `_AXUIElementGetWindow` (a private symbol, resolved at runtime via dlopen/dlsym, with capability degradation when missing, all unpublished ABI converged in `AXWindowIdentitySPI.swift`) proves no window maps to that id, it is reported as stale with the same error string as stale-window; when the check is indeterminate (symbol missing / no AX window list / any mapping failure) it never rejects, and does not use list-level heuristics such as alpha/layer/bounds). AX window matching for `get_window_state` / `activate_window` is identity-first: when the mapping is available it hits exactly by CGWindowID (same-bounds windows are no longer ambiguous, and screenshot/AX-tree mismatches are ruled out structurally); when the mapping is unavailable/incomplete it falls back to frame geometry + title/focused tie-break, and when multiple same-bounds candidates cannot be uniquely determined it throws the explicit error `ambiguousWindow(id): ...` instead of taking the first candidate. `get_window_state` defaults to `include_screenshot=true` / `include_text=false` (explicitly rejected when both are off), and the result is pretty-printed JSON (`window` + `accessibility.tree` (`focused_element`/`selected_text` gated by `include_text`) + `screenshots[]` carrying `id/url/width/height/originX/originY/zIndex`, `width`/`height` in window bounds points), with screenshots reusing the existing `WindowCapture`/ScreenCaptureKit capture chain; screenshot ids look like `shot-{windowID}-{n}`, are cached per window, invalidated by any successful action, and stale ids are rejected before execution (`stale screenshot id; re-observe with get_window_state before retrying.`); window-targeted actions on unobserved windows report `No window state is available for window id ...`. Window-targeted coordinate actions enforce the same observation gate as Windows (`call get_window_state before issuing coordinate input`, `call get_window_state with include_screenshot before issuing coordinate input`, `window bounds changed; call get_window_state before continuing`, `(x, y) is outside screenshot bounds`); element targeting and legacy `app`-keyed flows are unaffected. `activate_window` goes through unminimize → `NSRunningApplication.activate` → AXRaise + AXMain/AXFocused (≤3 attempts, 0.25s apart) and re-validates against the frontmost app / the app's focused window (on failure reports `activateWindow(id): the window could not be brought to the foreground; re-observe with list_windows.`), with no AppleScript/shell and no extra feature gate. All 5 Linux window2 tools still return an explicit "not supported yet" error.
- Windows `click_method=accessibility` maps to UI Automation patterns, and `app_post` maps to HWND `PostMessage`; the macOS-only `sky_click` explicitly returns unsupported before the snapshot lookup. Since 2026-08, `global` is available: after activating the target window it injects real pointer/keyboard events via `SendInput` (Go `realKeyChord`/`realTypeText`: chords use vk+scancode, text uses `KEYEVENTF_UNICODE`); the entire path is gated by `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOREGROUND_INPUT=1` (validated at both the service layer and the runtime layer), and when not enabled it returns a clear error including how to enable it rather than failing silently. The `auto` chain is upgraded to UIA → PostMessage → 250ms lightweight verification (Toggle/ExpandCollapse/SelectionItem state or focused-element change): if nothing changed and the flag is enabled, it activates the window and replays via SendInput; if the flag is not enabled it stops at PostMessage (consistent with the old behavior, not stealing the foreground). `press_key`/`type_text`/`scroll`/`drag` gain an optional `input_method` (`auto|global`), with the same semantics as for click.
- 2026-08-23 ABI/reliability fixes (review-driven): fixed keyboard packing of the `INPUT` union (on x64 `ki.wVk/wScan` overlaps `mi.dx` and `ki.dwFlags` overlaps `mi.dy`; the old code wrote scan into flags and the real flags were lost in padding, silently breaking `input_method=global` `press_key`/`type_text`); `SendInput` now returns and validates the injected count (reports `SendInput injected N of M events` when short, no longer silently dropped); `oleVariant` padded to the 24 bytes of an x64 VARIANT (the old 16 bytes allowed an 8-byte out-of-bounds write by COM out-parameters); UIA `GetCurrentPattern` null-pointer branch got a nil check + a recover on UIA thread jobs (panic downgraded to error); absolute coordinate normalization switched to the virtual screen (`SM_X/Y/CX/CYVIRTUALSCREEN` + `MOUSEEVENTF_VIRTUALDESK`, correct for multi-screen / negative-coordinate origins; the old implementation normalized against the primary screen, offsetting secondary-screen coordinates); MCP stdio switched to line-by-line frame reading (a bad frame gets one -32700 reply and serving continues; a streaming `json.Decoder` never consumes input again after a bad frame, spinning at 100% CPU); the snapshot cache only stores screenshot-stripped copies, capped at 16 entries; `click_count`/`pages` clamped at the service layer (≤100/≤1000). All of the above are pinned by unit tests (`native_abi_test.go`).
- Screenshot chain: `Windows.Graphics.Capture` (pure-Go implementation in native_capture.go, D3D11 staging texture reads, per-HWND FramePool/session caching + rebuild on size change + cleanup of invalidated windows, `put_IsCursorCaptureEnabled(false)` from 1903+ so screenshots exclude the system cursor) → `PrintWindow(PW_RENDERFULLCONTENT)` → GDI `CopyFromScreen`; the production path runs in the sacrificial subprocess (hidden `capture` subcommand). WGC can capture the actual content of an occluded window (aligned with official behavior; the GDI path captures the occluding object instead). `OPEN_COMPUTER_USE_WINDOWS_CAPTURE=wgc|print|gdi|auto` (default auto) can force a single mode, and a forced-mode failure errors out directly; the auto chain degrades step by step, treating an all-black sampled frame as a failure (following the Linux runtime's image-omission behavior).
- Aligned with the official documentation as actually shipped (2026-08-23, referencing the docs/api.md and docs/guidance.md of the built-in plugin of the Windows Store edition of the Codex app on this machine): `accessibility.document_text` of `get_window_state` (the value of the most relevant Document element, falling back to Edit, going through the text_limit pipeline) and `accessibility.selected_elements` (tree-format lines of SelectionItem elements currently in the selected state; verified on real hardware to capture the selected tab item in Notepad) are implemented; the method surface hits 13/13 (we additionally have the legacy get_app_state). `lastUsedDate`/`useCount` in `list_apps` are official optional fields ("when available"); Windows has no corresponding data source, so they are omitted. Not yet aligned (kept on file): the input method auto-activating the target window (the official model is foreground SendInput; we default to background without stealing focus), multiple bounded screenshots (transient UI / modal layering), SnapshotLease event-style invalidation, and the Run dialog / authentication dialog / settings page denies in the official guidance's hard-rejection list.
- Since 2026-08-25 the Windows runtime provides **display-level commands** with the same names as the Linux side (command names, arguments, and output JSON structure aligned item by item; see the command surface notes in the Linux Runtime section):
  - `open-computer-use.exe screenshot [--output x.png]`: GDI `BitBlt` reads the entire virtual desktop (`SM_X/Y/CX/CYVIRTUALSCREEN`, including all displays) as PNG; reuses the per-window screenshot chain's `captureGDIRegion`, converting BGRA→NRGBA before `png.Encode`.
  - `open-computer-use.exe cursor-position`: `GetCursorPos` + virtual desktop size, outputting the JSON `{x, y, screen_width, screen_height}` isomorphic to the Linux side.
  - `open-computer-use.exe input <move|click|drag|scroll|type|key|wait>`: reuses the SendInput layer of `input_method=global` (`realMouseMove`/`realMouseClick`/`realKeyChord`, etc.), sharing the `OPEN_COMPUTER_USE_WINDOWS_ALLOW_FOREGROUND_INPUT=1` gate with the tool surface; `input key` also enforces the Windows/Meta key hard rejection. Command construction is a pure function in `desktop.go` and has unit tests.
  - `open-computer-use.exe record <start|stop|discard|polish|status>`: `ffmpeg -f gdigrab` records the whole screen as H.264 mp4. The default `--quality demo` aligns with Cursor RecordScreen quality (veryfast/crf17/High/faststart); there is also `draft` (ultrafast), `--fps`, `--draw-mouse`, `stop --save-as`, and `discard`. While recording, display `input` appends to `<output>.events.json`; `record polish` (or `start`/`stop --polish`) defaults to the clean-room frame compositor (same pipeline as Linux: zoom/lens/motion-blur/cursor/keys; `--engine ffmpeg` / `--ripples` available), with `draw-mouse=0` as the default when `--polish` is set. `start` detaches ffmpeg with `CREATE_NEW_CONSOLE|CREATE_NEW_PROCESS_GROUP` (hidden window) and writes a pidfile; `stop` uses `AttachConsole` + `GenerateConsoleCtrlEvent(CTRL_BREAK_EVENT)` to let ffmpeg terminate gracefully (mp4 moov written to disk and playable); when the console dance is not feasible it hard-kills and explicitly warns the artifact may be unplayable; a missing `ffmpeg` is reported as a clear error.
- Windows UI Automation needs to run inside the desktop session of a logged-in user. When run as a detached background process over SSH, `open-computer-use.exe` can start and return JSON, but the system may not expose top-level windows to it; in that case `list_apps` will be empty and `get_app_state` may return `appNotFound(...)`.
- The Windows side is currently still a functional first version: no visual cursor overlay, no installer/onboarding, no code signing, and no standalone Windows smoke fixture.

### 6. Linux Runtime

- The Linux runtime lives in `apps/OpenComputerUseLinux` and maintains the CLI, `call --calls` sequence, MCP JSON-RPC, tool schema, and in-process snapshot cache in Go.
- The build entry is `scripts/build-open-computer-use-linux.sh --arch arm64|amd64`, outputting by default to `dist/linux/<arch>/open-computer-use`; the npm release package embeds the two Linux artifacts into the existing root/alias packages, and the Node launcher auto-selects based on `process.platform/process.arch`.
- Since 2026-08-23 the runtime is fully Go-native: the embedded `runtime.py` and the `python3` subprocess are removed, single binary with zero runtime dependencies (only two pure-Go modules, `godbus/dbus/v5` + `jezek/xgb`, no CGO). The layering matches the Windows side: `atspi_node.go` carries all pure logic aligned byte-for-byte with the retired Python bridge (error copy and behavioral quirks pinned by `atspi_node_test.go`), and the `//go:build linux` files `native_atspi.go` / `native_input.go` / `native_capture.go` / `native_backend.go` carry the real I/O. AT-SPI2 uses a two-hop D-Bus connection (session bus → `org.a11y.Bus.GetAddress` → a11y bus); the tree structure uses a per-app `Cache.GetItems` snapshot, non-cached data (extents/text/value/action) goes through live calls, keyboard/mouse synthesis goes through the registry's DeviceEventController, and screenshots decode X11 `GetImage` ZPixmap; text capability is detected by checking for `Text` / `EditableText` in the object's AT-SPI interface list.
- The closest thing on Linux to macOS AX is AT-SPI2/D-Bus accessibility, not a unified background keyboard/mouse input model. The first version prefers the AT-SPI action, EditableText, and Value interfaces exposed by the element; coordinate `click` / `drag` and `press_key` use the AT-SPI event synthesis fallback, which can only be treated as best-effort under Wayland.
- The Linux runtime needs to run inside a logged-in desktop user session. When the `XDG_RUNTIME_DIR`, `DBUS_SESSION_BUS_ADDRESS`, or display environment is missing, the Go runtime tries to auto-discover the current user's session bus, display / Wayland values from `/run/user/<uid>` and common desktop processes before connecting to the AT-SPI2 bus; a pure SSH tty that cannot find a logged-in desktop session can start the binary, but cannot directly inspect or operate a GUI session.
- The accessibility tree of `get_app_state` can be very deep on GTK/GNOME apps; the Linux bridge uses the same 1200-node, 64-level default tree budget as macOS / Windows, and supports explicitly raising `max_tree_nodes` / `max_tree_depth`. The screenshot is a best-effort capture of the X11 root window; under GNOME Wayland / rootless XWayland the read fails or returns a black image, in which case the bridge silently omits the image block (a black image is detected by 16×16 grid sampling).
- The protocol surface of these 9 tools is consistent with macOS / Windows: `list_apps`, `get_app_state`, `click`, `perform_secondary_action`, `scroll`, `drag`, `type_text`, `press_key`, `set_value`. Among them, element-targeted actions preferentially reuse the runtime path metadata from the previous `get_app_state` round, while coordinate actions use screenshot/window-relative coordinates.
- Linux `click_method=accessibility` maps to AT-SPI actions, and `global` maps to AT-SPI mouse synthesis and requires the global pointer environment variable; AT-SPI has no equivalent process-targeted mouse dispatch, so `app_post` and the macOS-only `sky_click` explicitly return unsupported before the snapshot lookup. `auto` keeps the existing behavior of preferring AT-SPI actions with a mouse synthesis fallback.
- Beyond the 9 AT-SPI2 tools, the Linux runtime also provides a set of **display-level X11 commands**, matching the "xdotool + ffmpeg + x11grab" stack of Cloud Agent / VNC hosts, to fill in the whole-screen operation and recording capabilities that AT-SPI cannot cover (the AT-SPI tools remain per-app and non-invasive). Since 2026-08-25, this command surface (command names, arguments, and output JSON structure of `screenshot`/`cursor-position`/`input`/`record`) has been implemented in alignment by the Windows and macOS runtimes (see the Windows Runtime and App Mode Layer sections above for per-platform backend differences):
  - `open-computer-use screenshot [--display :N] [--output x.png]`: pure Go (xgb) reads the entire X11 root window (including all displays) as PNG, reusing the same ZPixmap decoding as per-window screenshots; without `--output` it prints the base64 PNG to stdout.
  - `open-computer-use cursor-position [--display :N]`: pure Go (xgb `QueryPointer`) returns JSON with the pointer coordinates and screen size.
  - `open-computer-use input <move|click|drag|scroll|type|key|wait> [--display :N]`: performs **global** synthetic input via `xdotool` (moves the real pointer / keyboard, may change the foreground focus). Except for `wait`, all require `OPEN_COMPUTER_USE_ALLOW_GLOBAL_POINTER_FALLBACKS=1`, sharing the same process-level safety gate as the existing `click_method=global`; command construction is a pure function with unit-test coverage, and a missing `xdotool` is a clear error rather than a silent success.
  - `record <start|stop|discard|polish|status>`: records the whole screen as mp4 via `ffmpeg -f x11grab`. The default `--quality demo` aligns with Cursor RecordScreen quality (veryfast + crf 17 + High + faststart + all-intra; `--fps 60` is available to approach its capture frame rate), and `draft` keeps the old ultrafast. While recording, display `input` appends to `<output>.events.json`; `record polish` (or `start`/`stop --polish`) defaults to the clean-room frame compositor (idle remap → zoom → lens warp → motion blur → cursor + keystrokes; `--engine ffmpeg` for the old filters; `--ripples` forces ffmpeg), with `draw-mouse=0` as the default when `--polish` is set. `start` detaches a background ffmpeg, waits for writing to begin, and writes `{pid,output,display,fps,quality,…}` to the pidfile; `stop` sends SIGINT to wrap up, with an optional `--save-as`; `discard` stops and deletes the artifact and sidecar; `status` reads the pidfile and reports running state / byte count / event_count; a missing `ffmpeg` is reported as a clear error.
  - The `display` resolution order is `--display` > `$DISPLAY` > `:0` (VNC/AnyOS desktops are usually `:1`). These commands only take effect on Linux: the pure logic lives in `desktop.go`, the native X11/xdotool/ffmpeg implementations live in `desktop_linux.go` under `//go:build linux`, and `desktop_other.go` provides non-Linux stubs, guaranteeing the package compiles on any host and the pure-logic unit tests run anywhere. They are CLI-only and do not enter the official-aligned 14 MCP tool surface.
- The Linux side is currently still a functional first version: no visual cursor overlay, no installer/desktop entry, and no standalone Linux fixture.

- 2026-08-23 fixes (review-driven): `send_key` main-key parsing moved before pressing modifiers, and the error path releases already-pressed modifiers in reverse order (`ctrl+bogus` goes from "Ctrl stuck" to a zero-event error); MCP stdio switched to line-by-line frame reading (a bad frame gets -32700 and continues; a `json.Decoder` streaming bad frame spins at 100% CPU); `mouse_button` short names `r`/`m` correctly map to right/middle button, and illegal values are an explicit error (aligned with the schema enum; the old implementation silently used left button); the snapshot cache stores screenshot-stripped copies capped at 8 entries; `click_count`/`pages` clamped (≤100/≤1000). The uid-ownership check is split into `uid_linux.go` (non-Linux hosts compile a stub), and the pure-logic tests can run on any host.

## Key Boundaries

- The open-source edition currently does not replicate the caller signing, private IPC, full overlay choreography, and plugin self-install logic in the official closed-source implementation.
- The official `SkyComputerUseClient` carries host-side launch constraints and service-side sender authorization, so external raw stdio MCP clients cannot stably connect directly to the official bundled `computer-use`; when real use of the official tools is needed, the normal Codex agent/tool call chain should be used, while the open-source edition continues to provide a directly connectable `open-computer-use` MCP server.
- The current permission onboarding already has a runnable app, deep links, drag assistance, and a version of the accessory panel entrance animation and back affordance that is closer to the official one; the click chain has also been supplemented with an independent visual cursor, an official asset fallback, and ordering logic relative to the target window, and while the overlay is visible it keeps reasserting "above the target window", so that when the user manually activates the target app the cursor is not re-covered by the target window; overall, however, the official's embedded choreography / host integration / session approval experience has not yet been fully replicated.
- Screenshots currently capture the target window via `ScreenCaptureKit` and are returned as a base64 PNG in an MCP `image` content block; ordinary app screenshots are no longer written to disk in the repo or a temporary directory; before encoding they are adaptively downscaled by max dimension and target byte size, avoiding large PNGs from complex pages triggering host-side MCP result degradation, while coordinate tools continue to map coordinates by the actually returned screenshot pixel size; a single ScreenCaptureKit capture has a timeout set, and on timeout the image block is omitted rather than stalling the whole `get_app_state`.
- Session state is now in-process in-memory state, keeping each app's most recent snapshot and element index mapping.
